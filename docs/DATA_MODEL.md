# Модель данных: реестр решения

Главный технический актив агента. Ответы LLM превращаются из одноразового текста в проверяемую систему: у каждого вывода видно, откуда он взялся, и что сломается, если основание изменится.

## Где лежит

```
projects/<case>/
  sources/            ← материалы проекта (копии документов, таблицы, расшифровки)
  state/ledger/       ← реестр: по одному YAML-файлу на тип объекта
    sources.yaml  claims.yaml  hypotheses.yaml  pains.yaml  alternatives.yaml
    decisions.yaml  promises.yaml  experiments.yaml  changes.yaml
schemas/ledger.schema.json   ← JSON Schema всех типов
tools/ledger.py              ← validate / impact / trace / stats
```

## Цепочка

```
SRC источник ─► CLM утверждение ─► HYP гипотеза/допущение ─► ALT вариант ─► DEC решение ─► PRM обещание
                     │                     │                                   │
                     └► PAIN боль клиента  └──────────► EXP эксперимент ◄──────┘
CHG новые сведения ──воздействует на──► CLM/HYP/…
```

| Префикс | Тип | Ключевые поля | Что гарантирует валидатор |
|---|---|---|---|
| `SRC` | источник | kind, access (`open`/`own`), url/path, sha256, reliability | только открытые или собственные материалы; файл существует; хэш совпадает (иначе источник изменился → нужен CHG) |
| `CLM` | утверждение | type: `fact` / `forecast` / `interpretation`; evidence (source + quote/locator); confidence + rationale; contradicted_by | у факта есть evidence; факт не опирается на синтетическое интервью; **цитата действительно есть в тексте источника**; у прогноза и интерпретации есть основания |
| `HYP` | гипотеза / допущение | kind, based_on, verdict, would_change_decision | предупреждение, если гипотеза способна изменить решение, но эксперимент её не проверяет |
| `PAIN` | боль клиента | 5 критериев бизнес-ангела: частота, стоимость, обходные пути, незакрытость, измеримость — каждый с основаниями | у каждого критерия есть уровень (`unknown` допустим и честен) |
| `ALT` | вариант | kind: `invest` / `change` / `status_quo` / `kill`; objections (≥1); scores | у каждого варианта есть сильное возражение |
| `DEC` | решение | options (≥3), state, recommended, chosen, rejected, decided_by, owner, metrics, review_triggers | есть status quo (и предупреждение без kill); chosen входит в options; принятое решение заполнено полностью; **decided_by не может быть агентом** |
| `PRM` | коммуникационное обещание | message, audience, barrier, feature, proof, channels, decision | обещание привязано к функции продукта и решению |
| `EXP` | эксперимент | tests, expected_change, comparison, duration, side_effects, stop_go | все поля плана проверки из ТЗ обязательны |
| `CHG` | новые сведения | source, effects (target + weakens/strengthens/contradicts/retracts), processed | предупреждение, пока событие не обработано |

## Ключевые проектные решения

1. **Ссылки хранятся только вверх по цепочке** (объект указывает, на чём основан). Обратные связи (`used_in`) вычисляет `ledger.py`, поэтому рассинхронизироваться им не с чем. Это отступление от исходного плана, где `used_in[]` хранилось в claim.
2. **Записи не удаляются.** Статус `active` / `superseded` (+ `superseded_by`) / `retracted`. Память между сеансами не превращает прежний ответ в факт: отозванная запись видна, а всё, что на неё опирается, получает предупреждение.
3. **Impact analysis — детерминированный код, а не LLM.** `ledger.py impact` обходит граф в ширину и показывает путь до каждого затронутого объекта. LLM-агент только переформулирует затронутое, а незатронутое не трогает. Так пересмотр воспроизводим и проверяем в тестах.
4. **Проверка цитат встроена в валидатор** (вместо отдельного `citation_check.py`): для текстовых источников цитата ищется в файле без учёта регистра и пробелов.
5. **Один файл схемы и один CLI** вместо набора скриптов: меньше точек входа для агента и для жюри.
6. **Даты читаются как строки** (собственный YAML-загрузчик), поэтому агент может писать `2026-10-01` без кавычек.

## Команды

```bash
python tools/ledger.py validate projects/example          # 0 ошибок → можно продолжать
python tools/ledger.py impact   projects/example CHG-001  # что пересмотреть
python tools/ledger.py trace    projects/example DEC-001  # на чём держится решение
python tools/ledger.py stats    projects/example
python -m pytest -q tests
```

## Учебный пример `projects/example`

Вымышленный сервис «Заметки+», все данные учебные. Вопрос: «во что вложить квартал, чтобы остановить падение удержания?». 4 варианта (включая status quo и kill), решение «переписать синхронизацию». Новое событие CHG-001: опрос показал, что проблема затрагивает лишь 8% пользователей.

`impact CHG-001` затрагивает ровно 7 объектов: CLM-004, HYP-001, PAIN-001, ALT-001, DEC-001, PRM-001, EXP-001. Ветка позиционирования (ALT-002, HYP-002), status quo, kill и исходные факты не затронуты. Это закреплено тестом `test_impact_of_change_is_exactly_expected`.

Два предупреждения валидатора в примере оставлены намеренно: HYP-002 не проверяется экспериментом, CHG-001 не обработан. С ними работает агент на следующем шаге.
