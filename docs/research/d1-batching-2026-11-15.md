# Проверка пакетной обработки D1

Проверено 2026-11-15 в Codex. Задача: проверить объединение независимых
запросов пяти агентов и риск доставки ответа другому агенту.

## Результат

В установленном mlx-vlm 0.7.11 метод `system_one_batch` существует, но
`d1_lfm3_vl.d1.SystemOne.run` вызывает `_request` последовательно для каждого
элемента. `d1_hidden` формирует одну строку `h[None]`. Это пакетный интерфейс,
а не вычислительный batch независимых задач. Замена одиночного вызова пакетным
сама по себе не реализует параллельный inference. Численный выигрыш не измерен.

Источник: локальный `mlx-venv/lib/python3.12/site-packages/mlx_vlm/models/d1_lfm3_vl/d1.py`
в `~/.cache/strategist/d1-2b-lab`, строки 142 и 326.
SHA256: `301a008cff27646460f3ec2106c7d3c96197e25032fa811f28668fb06eaf0e36`.
Context7 вернул общую документацию batching генерации; она не доказывает
поддержку вычислительного batching для специализированного пути D1.

## Выполненные проверки

- Метод `SystemOne.run` извлечён через AST из установленного файла и выполнен
  с подменённым `_request`: для 1, 2, 5 входов получено соответственно 1, 2, 5
  отдельных вызовов; порядок и отдельные контексты сохранены. Веса не загружались.
- `pytest -q tests/test_d1_service_client.py tests/test_d1_service.py`:
  **47 passed in 14.48s**. В том числе чужой ID не принимается клиентом,
  повторный ID не исполняется заново, проверены отмена и истечение deadline.
- Новая проверка `tests/test_d1_reply_isolation.py`: **1 passed in 0.31s**.
  Пять конкурентных клиентов, настоящий UNIX socket и один тестовый subprocess;
  у каждого свой ID и отличающийся результат. Все получили свой результат.
  Inference подменён: это проверка транспорта, не качества D1.

## Решение и ограничения

Рабочий сервис и модель не переключались. Не включаем накопление пакетов:
при текущем последовательном движке оно может задержать ранние ответы.
Для настоящего batching нужен отдельный эксперимент с изменением вычислительного
пути: изоляцией attention, обработкой разных длин и сохранением калибровки.
Перед включением нужны сравнение ответов с одиночными, проверка перестановки
элементов, RAM/swap, latency каждого клиента и времени всей группы.

При будущем batching ID назначает и связывает с клиентом сервис, а не модель.
Клиент получает только свой результат. Проверять нужно не только внешний ID,
но и соответствие содержимого исходной задаче: правильно подписанный чужой
ответ проверка ID сама по себе не обнаруживает. Нельзя склеивать пять контекстов
в один общий промпт и считать это изолированным batching.
