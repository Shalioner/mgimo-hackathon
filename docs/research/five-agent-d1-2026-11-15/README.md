# Пять агентов → один D1: нагрузка, маршруты, качество и расходы

Дата: 15.11.2026. Среда: Codex 0.169.0, native account; локальный MLX D1-2B 8bit
на Mac с 8 ГБ. Модель и revision закреплены в receipts. Код, кейсы, порядок и
лимиты зафиксированы до запуска в [manifest.json](manifest.json) и
[протоколе](../../../evals/routing/FIVE_AGENT_PROTOCOL.md).

## Главное

Пять одновременных клиентов обслуживаются одним D1 worker, но устойчивость холодной
загрузки на этой машине не подтверждена: первый раунд остановлен защитой памяти.
Во втором раунде один PID обработал все 10 запросов. Очередь добавляла до 33.19 с,
а полный ответ D1 занимал до 39.54 с. Восемь из 10 выборов потребовали T1-review.
Маршрутизация уменьшила расчётную стоимость облачных моделей, но не сохранила
качество и полноту выдачи. Заявлять доказанную экономию для жюри сейчас нельзя.

## Что именно запускалось

Пять самостоятельных процессов-агентов, у каждого свой кейс и два шага. На каждом
шаге запросы стартовали одновременно через barrier. Все пользовались одним UNIX
socket и одним последовательным worker D1. Это реальные native model calls через
app-server, но не пять автономных Orca UI-сессий и не полный C1–C3 продуктовый E2E.
Между заданиями создавались новые ephemeral threads; фиксированные материалы
второго шага одинаковы для обеих веток, история ответов в следующий вход не добавлялась.

Кейсы: извлечение→план; окна удержания→расчёт; сегменты→стандартизация;
экономика вариантов→stop; обещания→сообщение и проверки. Все сведения синтетические.
Manual control заранее назначает Luna/Terra/Sol и effort по каждому шагу.
Quality gate и эскалация одинаковы: до 2 попыток, T4 запрещён. D1 timeout120 с;
постоянные настройки проекта не менялись. Порядок routed→manual→manual→routed.
Итого 40 задач: по 20 на ветку,10 уникальных заданий с двумя повторениями.

## Скорость D1 и очередь

Первый раунд: worker остановлен при `Critical system memory pressure`;0 успешных
классификаций. Все 10 задач получили manual, облачные исполнения не запускались.
Неудачный раунд сохранён, не заменён удачным. Замер памяти после отказа показывает
pressure=1 и swap3744MiB: это **последующий снимок**, а не измеренный пик.

Второй раунд:10/10 запросов D1 успешно, worker PID26167, generation2 для всех.
Смешивания request ID и отказов `busy` в этом раунде не зарегистрировано.

| Стадия, успешные 10 запросов | Медиана | Максимум |
|---|---:|---:|
| Ожидание очереди | 14.563 с | 33.191 с |
| Вычисление внутри engine | 4.195 с | 7.893 с |
| Полное время сервера | 19.839 с | 39.506 с |
| От отправки клиентом до получения JSON | 19.843 с | 39.540 с |

Один холодный setup занял 15.220 с; остальные setup — менее миллисекунды.
Engine timing включает подготовку, tokenizer, forward, синхронизацию и проверки;
это не отдельный GPU-kernel benchmark. Client-server разница включает IPC и
сериализацию, поэтому не называется чистым временем передачи.
Дефолтный host deadline30 с меньше наблюдаемого максимума:120 с использовались явно
по протоколу. Работа пяти клиентов с прежним 30 с deadline этим не доказана.

## Реальная последовательность моделей

Ниже только фактически переданные модели основных задач второго routed-раунда.
План маршрута не считается исполнением, переходы к reviewer/verifier вынесены отдельно.

| Кейс | Шаг 1 → шаг 2 |
|---|---|
| C1: извлечение → план | Luna/low → Luna/low |
| C2: разные окна → расчёт | Luna/low → Luna/low |
| C3: сегменты → стандартизация | Sol/xhigh → Luna/low |
| C4: варианты → stop | Sol/high → Luna/low |
| C5: обещания → проверки | Luna/low → Luna/low |

Фактических смен модели основных задач: **2**. Повышений effort внутри задачи
в routed не было. Sol/xhigh выбран сразу, это не эскалация high→xhigh.
T1-review понадобился 8/10 запросов; он вместе с D1 определял итоговый маршрут.
Выбор T4 с низкой уверенностью в raw D1 не привёл к запуску Astra.

Manual baseline в каждом раунде: Luna/low→Terra/medium; Terra/medium→Luna/low;
Sol/high→Terra/medium; Sol/high→Luna/low; Luna/low→Terra/medium.
Во втором manual C5 шаг 2 действительно повысился Terra/medium→Terra/high после
quality `revise`. Всего 10 межшаговых смен модели и 1 повышение effort в двух
manual-раундах. Это заранее назначенные маршруты контроля, не заслуга D1.

## Качество: найденные проблемы

Встроенный gate подтвердил 4/20 routed и 13/20 manual задач. Отдельному Sol/high
в новом text-only контексте переданы 30 полученных ответов/кандидатов в перемешанном
порядке, без ветки, модели и статуса выдачи. По этой **модельной**, не человеческой
проверке: manual20/20 кандидатов корректны; routed8/10. Не выданные кандидаты
не считаются успешно выполненными задачами. У выданных 4 routed и 13 manual ответов
смысловых дефектов этот судья не нашёл. Один судья не доказывает общую точность.

Конкретные дефекты:

1. **Quality gate и JSON-экранирование:**13 ответов проверяющего `accept/sure=true`
   остановлены literal quote check. Цитаты скопированы из JSON-ответа, но state
   содержит его как повторно экранированную строку. Это влияет на обе ветки.
2. **Ошибочная дешёвая модель/проверка:** C3 шаг 2 routed дал 62.5% и+12.5 п.п.
   вместо 57.5% и+7.5 п.п. T1-verifier ответил accept. Literal mismatch случайно
   удержал выдачу. Нельзя просто ослабить quote gate: нужна содержательная проверка
   расчётов, желательно T0, и повторный тест выбора модели.
3. C5 шаг 2 routed не составил полноценные две проверки с условиями допуска обещаний.
4. Механический scorer отдельно отмечает несовпадения JSON-схемы; вложенное поле
   `status` вместо строки не приравнивается к смысловой ошибке. Поэтому число
   механических passes (2 routed,11 manual выданных) не заменяет слепую оценку.

После получения результатов пороги, вопросы и gate не менялись и плохие ответы
не перезапускались. Следующая работа: устранить представление JSON для verifier
без ослабления доказательности, ввести проверку вычислений, разобраться с частыми
T1-review и ресурсами холодной загрузки, затем новый заранее зафиксированный прогон.

## Изменения и проверка реализации

Исправлена admission-гонка: теперь принимаются active1+waiting4, даже если пять
запросов пришли до первого dequeue. Добавлены monotonic timing и частичные значения
при timeout. Отдельного cancel-by-ID нет: disconnect не равен отмене. Лимиты памяти
и sandbox сохранены. Сервис перезапущен штатным `d1_control stop/start` до теста.

Независимое ревью проверило service patch и harness. Исправлены потеря невыданных
строк в знаменателе, подсчёт plans как switches, потеря receipts при ошибке шага.
Полный Python suite: **828 passed,1 skipped**. Skip — необязательный openpyxl.
