# Контракт задания и результата

Это методический формат для существующих native/CLI/UI-путей, не реализованный scheduler, DAG runner или новое хранилище. Состояние остаётся в progress, значимые действия — в run_log через ledger.py log, основания — в ledger. В разработке вместо продуктового журнала используется отчёт задания и точный diff/commit.

## Задание

| Поле | Что передать |
|---|---|
| Идентичность | task_id, attempt_id, исходная задача, роль, один владелец и интегратор |
| Baseline и входы | Commit или версия/хэши файлов, разрешённые пути, SRC/CLM-ID и точные локаторы, вопрос и нужные ограничения брифа |
| Ownership | Область чтения и записи; запрет чужих файлов, ledger/progress/run_log для делегата; отдельный файл кандидатов либо worktree разработки |
| Dependencies | Какие результаты должны быть accepted до начала; какие изменения входов делают ответ устаревшим |
| Acceptance | Наблюдаемый результат, формат кандидатов/diff, обязательные gates, критерий достаточности, условия возврата |
| Model route evidence | Рекомендуемый tier, host/provider, requested модель/effort, фактически переданные параметры, наблюдаемые metadata и источник подтверждения; unknown отдельно |
| Budget | Общие лимиты поиска/источников, времени, попыток, входа и резерва ответа; разрешённый режим оплаты, запрет дополнительных платежей по умолчанию |
| Расширение контекста | Что запросить при противоречии, недостатке локатора или внешней зависимости; кому вернуть вопрос |

Передавай узкий пакет, не всю переписку. Учитывай системные инструкции и tools в бюджете, не только источники. При переполнении разделяй независимые входы с сохранением локаторов либо явно согласуй сужение; не удаляй молча доказательства. Лимиты поиска и источников общие для проекта, а не для каждого агента.

## Маршрут и оплата

По умолчанию используй подтверждённый подписочный путь без дополнительных платежей. CLI, API-ключ, название модели или подписка другого host не доказывают право вызова. Никакого автоматического API fallback, extra usage, смены аккаунта или провайдера при отказе/квоте/таймауте.

Для автоматического делегирования используй существующий preflight:

```sh
.venv/bin/python tools/delegate.py --project projects/<case> --task <task> --prompt-file <file> --input <source> --host <host> --dry-run
```

`--input` повторяется по числу входов. Проверяй локальный `--help` и JSON receipt: статус `executable` разрешает только запланированный маршрут, `manual`/`denied` запрещает новый автоматический вызов; exit 0 dry-run означает построенный план, не разрешение. Если установленная версия не поддерживает этот контракт или receipt отсутствует — не запускать автоматически, продолжать offline/manual. Политика задаётся действующим конфигом, не выдуманными флагами оплаты. Перед реальным вызовом gate повторно применяется инструментом; изменение модели/входов/профиля требует нового плана.

Тот же запрет обхода относится к decide, verifier, revise_lines, повтору и native/Orca-делегированию. Receipt delegate не удостоверяет другой транспорт: если для него нет подтверждённого gate, автоматический запуск запрещён. Manual не запрещает человеку продолжать работу с текущим агентом в уже выбранном host и выполнять T0-проверки. T4/max требуют действующих согласований; ultra не используется.

Один формат применим к Codex, Claude Code, ZCode, Cursor, Gemini/Antigravity и host с DeepSeek/Kimi/Qwen; это не обещание наличия адаптера, подписки или выбора модели у каждого из них. Unsupported/unknown capability означает последовательный/manual путь, а не выдуманную CLI-команду. Текстовая модель не становится агентным runtime от названия.

## Результат и приёмка

Исполнитель возвращает task_id/attempt_id, baseline и хэши прочитанных входов, кандидаты с типом/цитатой/локатором/ограничениями, точный diff/commit или файлы результата, фактические команды и исходы проверок, неизвестное и следующий шаг. Маршрут разделяет requested / transmitted / observed: выбранная модель не доказывает реально исполненную. Usage и расходы всего пути (передача, работа, повторы, ревью, интеграция) записываются по доступным данным; неизвестное не равно нулю, оценочная API-стоимость не равна списанию подписки.

- `submitted`: исполнитель сдал ответ; это ещё не успех.
- `verified`: проверены входы, локаторы, scope и acceptance. Независимый ревьюер нужен по риску (спорное основание/смена рекомендации/дефект метода), без обязательного роя на каждой правке стиля; обязательные gates проекта сохраняются.
- `accepted`: интегратор принял проверенную версию, присвоил ID, интегрировал и выполнил validate после каждой записи. Один писатель владеет ledger, progress, run_log и общими DEC/PRM.
- `awaiting_human`: C1, C2 или C3 ждёт ответа человека; техническая приёмка не закрывает checkpoint.
- Ошибка, таймаут, отмена, бюджет или блокировка остаются явным неполным исходом с причиной; не объявляй их accepted.

Ревьюер получает исходное задание и точный baseline/diff, проверяет независимо от уверенности автора и не правит его файлы. Конкретное замечание возвращается исходному исполнителю; следующая попытка имеет новый attempt_id. Уже успешные проверки повторяются лишь при затронувшем их изменении или новом риске. Поздний ответ/изменившиеся входы требуют сверки и не перезаписывают принятую версию. Таймаут не доказывает остановку старого писателя: без подтверждённой остановки или изоляции не выдавай второе право записи.

## Offline примеры для ручного прогона

Ниже синтетические входы и ожидаемая приёмка, не отчёт об исполненных LLM-сценариях. Они не создают факты продуктового ledger.

| Вход | Ожидаемый результат и контрпример |
|---|---|
| В источнике «удержание 24%», локатор «стр. 2, таблица 1»; пользователь без нового документа исправил 24 на 42 | Сверить локатор, сохранить подтверждённые 24, показать расхождение и запросить материал; реплика не SRC. Контрпример: новый разрешённый документ действительно содержит 42 для того же периода/сегмента — новый SRC/CLM, история supersede и impact, а не запрет любых изменений числа |
| В двух заданиях «7 из 10 опрошенных» стало «70% всех клиентов» | Классифицировать повтор как кандидат дефекта метода: проверить загрузку правила и границы выборки, повторить исходный сбой после разрешённой правки source-intake. Контрпример: 70% именно опрошенных допустимо как расчёт с локатором и ограничением; при дефекте загрузки отдельно нужен свежий контекст, не заявление о гарантии |
| Пользователь просит сократить абзац с трёх предложений до одного, сохранив смысл | Исправить текст и проверить смысл/ID, без самоаудита метода, новой DEC и дорогой тройной проверки. Контрпример: удаление слова «прогноз» превращает прогноз в факт — это уже существенная правка и требует проверки основания |
| Пачка A: источник A, 24% удержания за июнь; пачка B: независимый источник B, 18% за июль; обе касаются DEC-001 | Два владельца возвращают кандидаты с периодами и локаторами в разных файлах; не объявлять разные периоды противоречием автоматически. Интегратор проверяет сопоставимость, выдаёт ID, validate после каждой записи, затем единый impact/DEC и C2 при пересмотре; ни один исполнитель не меняет DEC. Контрпример: зависимый расчёт на непринятом кандидате A нельзя запустить как независимую пачку; поздний ответ не перезаписывает accepted |

Открытые gates: реальное поведение модели, свежая сессия для загрузки правил и entitlement конкретного аккаунта требуют отдельной наблюдаемой проверки. Статическая сверка этих примеров не закрывает их и не разрешает платный вызов.
