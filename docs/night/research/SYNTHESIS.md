# S-01: что перенять из исследования

## Главное

Победители из карточек соединяют несколько источников и собирают отдельный итог с основаниями: [Chathletique](cards/B-colinfrisch-chathletique-mcp.md), [Apollo](cards/B-manasseh-zw-apollo.md), [RiskWise](cards/B-oh-qi-qi-azure-ai-agent-hackathon-2025.md).
У нас уже есть реестр, проверка ссылок и разделение исследования и стратегии; пробел этого среза — нет отдельного контракта результатов неудачного сбора и набора проверок ответа на ложную предпосылку без чисел.
Главное действие: сначала сделать малую проверку исходов сбора, чтобы руководитель не принял недоступность данных за отсутствие спроса.
Уверенность в наблюдениях ограничена чтением карточек; перенос и ожидаемый выигрыш ниже — наши предложения, ещё не результаты испытаний.

## Границы среза

Baseline: `959c7d67b0c3f8e35b1d34ba0bc6b83954e026bd`, ветка `night/S-01`. Рассмотрены все 10 карточек, присутствующих в этом baseline и [индексе](index.tsv); поздние ветки исследователей не учитываются. Вердикт «нет» в карточке относится к переносу предложенного решения, а не к приёмке самой карточки.

Доказательства победы указаны только у [Chathletique](cards/B-colinfrisch-chathletique-mcp.md), [Apollo](cards/B-manasseh-zw-apollo.md) и [RiskWise](cards/B-oh-qi-qi-azure-ai-agent-hackathon-2025.md). [Chellenge](cards/A-hfuvoo-art-chellenge.md) — участник; у остальных карточек результат неизвестен. Поэтому заголовок «Паттерны победителей» ниже обозначает заданный раздел, а счётчики относятся ко всему корпусу карточек, не к числу победителей. Совпадение паттерна с победой не доказывает причинную связь.

Сопоставление с нами: [карта критериев](../../CRITERIA.md), [обзор конкурентов](../../COMPETITORS.md), [официальное ТЗ](../../TZ_OFFICIAL.md). Старые оценки пробелов в обзоре не равны текущему состоянию: в baseline уже приняты T01, T03, T04; `datacheck.py` существует. T02 не принят, T05 не завершён, T07 зависит от T02 — см. [статус среза](../reports/STATUS.md). Данные конкурентов из обзора не перенесены сюда как новые проверенные факты о проектах без карточек.

Проверка текущей папки: [source-intake](../../../skills/source-intake/SKILL.md) требует CLM по вопросам плана, фиксации противоречий и ограничений; [situation-map](../../../skills/situation-map/SKILL.md) уже требует «что неизвестно / почему / как узнать». [Тесты verify](../../../tests/test_verify.py) уже проверяют число без ссылки, несуществующие и устаревшие ID. Ниже предлагается дополнить эти механизмы, а не создавать их заново.

## Что перенять

Ранжирование качественное: ожидаемый вклад в критерий / оценка ИИ-времени. Все минуты — плановые допущения автора, не замеры и не обещание прироста баллов. **Наблюдение** — только то, что записано в карточке; **перенос** — наша гипотеза, не заявленная возможность чужого проекта. Новая установка, модель, сервис или изменение реестра не нужны.

## Кандидаты на ночную реализацию

Два кандидата из пунктов 1–2; каждый независимо укладывается в ≤60 мин ИИ. Это **черновики будущих контрактов**, команды ниже ещё не существуют и в S-01 не выполнялись. Координатор должен выделить исполнителю отдельную область; Синтезатор меняет только этот документ и отчёт. Python stdlib и имеющийся PyYAML достаточны; сети, модели и установки сверх текущего окружения нет. Результат служит агенту внутри папки проекта.

1. **Исходы сбора — пункт 1, 35 мин.** Зона будущей работы: `tools/source_outcomes.py`, `tests/test_source_outcomes.py`, новые `tests/fixtures/source_outcomes/`; один абзац в `skills/source-intake/SKILL.md`. Вход — явно переданный JSON со списком `question`, `target`, `outcome`, `reason`, `next_check`; для `ok` дополнительно `source_id`, проверяемый по переданному проекту. Для неуспеха нельзя подставлять фиктивный SRC. Команда только читает; выдаёт счётчики и список ошибок. Коды: 0 — контракт полон, 1 — неполон, 2 — вход не читается. Непустой список обязателен; полноту охвата всех попыток она не обещает.

   | Команда будущей приёмки | Ожидаемый результат |
   |---|---|
   | `.venv/bin/python tools/source_outcomes.py tests/fixtures/source_outcomes/mixed.json --project tests/fixtures/source_outcomes/project --json` | Код 0; 4 исхода, по одному `ok`, `empty`, `unavailable`, `partial`; три неуспеха с причиной и следующим действием, 1 существующий SRC только у `ok`. |
   | `.venv/bin/python tools/source_outcomes.py tests/fixtures/source_outcomes/no_reason.json --project tests/fixtures/source_outcomes/project --json` | Код 1; точная строка неуспеха без причины; `empty` не превращается в положительный факт об отсутствии спроса. |
   | `.venv/bin/python -m pytest -q tests/test_source_outcomes.py -k invalid_contract` | Код 0; пустой список, неизвестный статус, ложный SRC и отсутствие `next_check` выявлены; нечитаемый JSON даёт код 2. |
   | `.venv/bin/python -m pytest -q tests/test_source_outcomes.py -k read_only_offline` | Код 0; входы побайтово сохранены; вызовы сети и LLM запрещены тестом. |

   Тест МегаФона: сбор → картина надёжнее; причины и ID доступны проверке; остаётся локальный инструмент; выигрыш измеряется полнотой трёх проблемных исходов. Успех команды не означает, что спрос исследован или отсутствует.

2. **Отрицательные ответы — пункт 2, 45 мин.** Зона будущей работы: `evals/evidence_limits/PROTOCOL.md`, `evals/evidence_limits/score.py`, `evals/evidence_limits/cases.json`, новые `tests/test_evidence_limits.py` и `tests/fixtures/evidence_limits/`. В `cases.json` фиксируются вопрос, доступные выдержки, ожидаемые неизвестные и допустимые основания; отдельные сохранённые ответы содержат `unknowns`, `conclusions`, `refs`. Scorer проверяет контракт, существование refs и требуемое обозначение пробела, возвращает `scope: structural_only`. Саму смысловую поддержку утверждения он не решает: для каждого результата обязательно `semantic_support: not_checked`, даже когда все структурные поля допустимы; статусы `grounded` и `semantic_pass` scorer никогда не присваивает. Код 0 — все контрольные ответы соответствуют структурной разметке, 1 — расхождение, 2 — невалидный вход.

   | Команда будущей приёмки | Ожидаемый результат |
   |---|---|
   | `.venv/bin/python evals/evidence_limits/score.py --cases evals/evidence_limits/cases.json --answers tests/fixtures/evidence_limits/good.json --json` | Код 0; 3 случая: ложная предпосылка, отсутствующая экономика и подтверждённый контроль; `scope: structural_only`, у неизвестных есть «почему» и «как узнать», у контрольного вывода — допустимый ref. |
   | `.venv/bin/python evals/evidence_limits/score.py --cases evals/evidence_limits/cases.json --answers tests/fixtures/evidence_limits/bad.json --json` | Код 1; ровно 2 заранее внесённых дефекта: ложная предпосылка принята без пробела и заключение с отсутствующим ref; корректный контроль не отвергнут. |
   | `.venv/bin/python -m pytest -q tests/test_evidence_limits.py -k paraphrase_limit` | Код 0; на заранее размеченном примере с формально допустимыми полями у каждого результата явно `semantic_support: not_checked`, статусы `grounded` и `semantic_pass` отсутствуют; тест проверяет только эту границу и необходимость ручной смысловой проверки, а не распознавание неподтверждённого смысла. |
   | `.venv/bin/python -m pytest -q tests/test_evidence_limits.py -k invalid_read_only_offline` | Код 0; неизвестный case-ID и отсутствующий файл дают код 2; фикстуры не изменяются; сетевых, модельных и агентных вызовов 0. |

   Тест МегаФона: запрос → картина → варианты защищён от неподтверждённой предпосылки; эталоны связаны с выдержками, неизвестное явно обозначено; это папка примеров и скрипт; проверяем обнаружение двух дефектов при нулевом ложном отказе на контрольном ответе. Изменение реального поведения агента остаётся непроверенным до отдельного разрешённого прогона и смыслового ревью.

## Чего не делать

- Не переносить приложение целиком: облачные сервисы, базы и UI [Apollo](cards/B-manasseh-zw-apollo.md), [RiskWise](cards/B-oh-qi-qi-azure-ai-agent-hackathon-2025.md), внешние аккаунты и сервер [Chathletique](cards/B-colinfrisch-chathletique-mcp.md) не проходят вопрос 3 теста МегаФона. Их маленькая методика не запрещена этим отказом.
- Не добавлять установщик и автономное управление сервисами [Astero81](cards/A-astero81-ai-product-factory.md) или runtime [DeerFlow](cards/B-bytedance-deer-flow.md). У нас сохранённое состояние уже есть; польза нового сервиса не показана.
- Не внедрять многоканальный движок [last30days](cards/B-mvanhorn-last30days-skill.md) ради пункта 1: нужен только контракт неполного покрытия. Не переносить многошаговую генерацию и модельные диалоги [STORM](cards/B-stanford-oval-storm.md) ради пункта 3: достаточно вопросов в текущем плане; синтетический ответ не становится фактом.
- Не заводить четыре экспертных контекста из [Fighter90 skills](cards/A-fighter90-product-decision-skills.md) ради числа ролей и не считать согласие аудиторов основанием. [ТЗ, раздел «Устройство»](../../TZ_OFFICIAL.md#устройство): «Число агентов, объём инструкций и новизна технологий сами по себе не преимущество: каждый компонент должен оправдывать свою сложность пользой».
- Не переносить повторно проверки, уже похожие на наши, из [Chellenge](cards/A-hfuvoo-art-chellenge.md); не выдавать метаданные, число файлов и победу в другом конкурсе за измеренную пользу нашей стратегии.
- Не обещать баллы или качество LLM по успеху структурного скрипта. Прогноз пользы требует собственного сравнения до/после; синтез и одобрение идеи его не заменяют.
