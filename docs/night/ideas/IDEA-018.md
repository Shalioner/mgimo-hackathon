# IDEA-018: Проверять тип прямо возле ссылки
- Критерий ТЗ: кр.1
- Цитата ТЗ: «факты отделены от гипотез и прогнозов»
- Новизна: ни у кого в проверенных [COMPETITORS](../../COMPETITORS.md), [Fighter90 decision skills](../research/cards/A-fighter90-product-decision-skills.md) и [llm-space](../research/cards/B-deer-flow-llm-space.md) не описана именно детерминированная сверка явной метки типа возле конкретного ID с типом объекта реестра. Реестр с типами и общие валидаторы у других есть; вывод ограничен этими описаниями, не всем кодом конкурентов.
- Что сделать: добавить к существующему `verify.py` режим `--type-labels`: сверять пары `[CLM-NNN] (факт|прогноз|интерпретация)` и `[HYP-NNN] (гипотеза|допущение)` с CLM.type/HYP.kind; английские эквиваленты fact/forecast/interpretation/hypothesis/assumption также допустимы. Проверять и строки без чисел. Отсутствие однозначной пары выводить отдельно как `untyped_reference`, не угадывать тип по словам абзаца. В `skills/situation-map/SKILL.md` закрепить уже близкую шаблону запись «ID → явная метка» и вызов этого режима перед передачей картины на шаг вариантов. Это проверка согласованности меток, не новый смысловой оценщик.
- Польза, которую можно измерить: в 4 размеченных строках без чисел выявить ровно 2 несоответствия: forecast назван фактом и assumption названа гипотезой; верные fact и forecast не отвергать. До — существующая числовая проверка ссылок не сравнивает такие явные метки; после — файл, строка, заявленный/реестровый тип видны в 1 вызове, без LLM. Непомеченные ссылки раскрываются отдельным счётчиком, а не повышают процент проверки смысла.
- ИИ-время: ~35 мин
- Риск: правильная метка может сопровождать неверный текст; неоднозначные конструкции, таблицы с отдельной колонкой «Тип», косвенные перефразировки и заявления «источник прогнозирует» этот узкий режим не интерпретирует. Выход всегда `scope: explicit_adjacent_labels_only`, `semantic_support: not_checked`; отсутствие ошибок не означает, что весь документ правильно отделяет факты.
- Зона правок: существующие `tools/verify.py`, `skills/situation-map/SKILL.md`, `tests/test_verify.py`; новые фикстуры `tests/fixtures/type_labels/**`. Схема реестра и ночные проверки не меняются.
- Черновик приёмки:
  1. `.venv/bin/python tools/verify.py tests/fixtures/type_labels/mixed --files 03 --type-labels --json` → код 1; ровно 2 type_label_mismatch с файлом, строкой, ID и обоими типами; четыре исходные строки не содержат чисел вне ID.
  2. `.venv/bin/python tools/verify.py tests/fixtures/type_labels/matching --files 03 --type-labels --json` → код 0; корректные русские и английские метки совпадают, scope и semantic_support указаны.
  3. `.venv/bin/python -m pytest -q tests/test_verify.py -k type_labels_ambiguous_and_missing` → код 0; ссылка без соседней метки и несколько ID в общих скобках дают untyped_reference, тип не выводится из лексики; несуществующий ID остаётся ошибкой ссылки, а не подставленным типом.
  4. `.venv/bin/python -m pytest -q tests/test_verify.py -k type_labels_read_only_and_integration` → код 0; входы неизменны, сеть/LLM не вызываются, прежний режим verify сохраняет контракт, навык situation-map явно вызывает --type-labels на выходе шага 4.
- Почему не дубль: IDEA-001 проверяла копии файлов, IDEA-006 — условность PRM на незавершённом EXP, остальные IDEA не сопоставляют явную метку в outputs с реестром. S-03 проверяет допустимые refs/обязательные пробелы в эталонном ответе; здесь ID может быть полностью действительным, а ошибка — подмена его типа в читаемом тексте. Это не повтор отрицательного теста «нет ссылки» и не переименование отклонённого инструмента. T01–T07 и I-01/02/03 этот режим не добавляют; gate проверки наличия меток не равен их сверке с реестром.
- Тест МегаФона: 1 картина → варианты: руководитель замечает прогноз, ошибочно подписанный фактом · 2 эталон типа — реестр, смысловая поддержка честно не проверена · 3 один режим существующего verify с вызовом из навыка · 4 на 4 строках находятся 2 заданные подмены, без ошибочного отказа на 2 контрольных строках.
