# IDEA-007: Пороги проверки нельзя менять незаметно
- Критерий ТЗ: кр.1
- Цитата ТЗ: «ожидаемое изменение, с чем сравниваем, срок наблюдения и нежелательные последствия.»
- Новизна: есть у [llm-space](../research/cards/B-deer-flow-llm-space.md) близкий приём — снимок версии рубрики оценивания; переносим его на условия продуктового эксперимента, а не приложение. Правило «stop/go заранее» уже есть у нас в `skills/validation-plan`, но отдельного сравнения условий EXP до и после результата среди инструментов нет.
- Что сделать: один инструмент `tools/experiment_lock.py record|check <project> --experiment EXP-NNN --snapshot <file> --json`: `record` сохраняет явно названный новый JSON-снимок полей `tests`, `expected_change`, `metric`, `comparison`, `duration`, `side_effects`, `stop_go` только у EXP без результата; `check` сравнивает эти поля с текущей записью и показывает старое/новое значение каждого изменения. Снимок создаётся без перезаписи; поля реестра не меняются, сравнение ничего не записывает. Наличие снимка доказывает только неизменность относительно сохранённого файла, не реальное время начала внешнего эксперимента.
- Польза, которую можно измерить: до — изменение порога в том же EXP требует ручного поиска истории; после — 1 команда находит сдвиг `stop_go` и смену `comparison`, но не считает добавленный `result` сменой плана. На контрольных данных 2 подмены условий дают ровно 2 различия; сохранение результата без правок плана — 0 различий.
- ИИ-время: ~40 мин
- Риск: добросовестная поправка плана тоже потребует объяснения человеку; это сигнал пересмотра, не запрет полезного изменения. Файл не защищён от согласованной ручной подмены снимка и реестра; инструмент не называет его подписью, пререгистрацией с независимой датой или доказательством качества эксперимента.
- Зона правок: `tools/experiment_lock.py`, `tests/test_experiment_lock.py`, новые `tests/fixtures/experiment_lock/**`.
- Черновик приёмки:
  1. `.venv/bin/python -m pytest -q tests/test_experiment_lock.py -k record_and_result_only` → код 0; запись в свежий tmp_path создаёт снимок, добавление только `result` сохраняет код проверки 0 и 0 различий; исходный проект побайтово сохранён.
  2. `.venv/bin/python tools/experiment_lock.py check tests/fixtures/experiment_lock/changed --experiment EXP-001 --snapshot tests/fixtures/experiment_lock/before.json --json` → код 1; ровно 2 различия: `stop_go` и `comparison`, оба со старым и новым значением.
  3. `.venv/bin/python -m pytest -q tests/test_experiment_lock.py -k missing_fields_order_and_wrong_id` → код 0; отсутствие необязательного `metric` воспроизводимо, перестановка YAML-ключей не меняет результат, другой EXP-ID или отсутствующий снимок даёт код 2.
  4. `.venv/bin/python -m pytest -q tests/test_experiment_lock.py -k no_overwrite_finished_and_offline` → код 0; повторная запись поверх снимка и запись EXP с результатом отклонены кодом 2 без изменений, `check` ничего не пишет, сетевых и модельных вызовов 0.
- Почему не дубль: T03 публикует прошлые замеры инструментария, T04 проверяет качество чисел в таблице, T05 создаёт план эксперимента; здесь руководитель проверяет неизменность конкретных заранее сохранённых условий EXP. IDEA-002 меняет веса для сценарного анализа, 004 сравнивает абзацы outputs и человеческий выбор, но не поля EXP; I-01 относится к очереди дат. Ни предыдущие IDEA, ни кандидаты SYNTHESIS не фиксируют условия продуктовой проверки. IDEA-009 относится к версии вопроса C2, не к последующему измерению эффекта продукта.
- Тест МегаФона: 1 стратегия → сопровождение: результат сравнивается с тем планом, который руководитель видел до измерения · 2 старые значения сохранены, смысл и внешнее время эксперимента не объявляются доказанными · 3 локальный JSON рядом с проектом и скрипт без нового runtime · 4 2 внесённые подмены обнаружены, добавление только результата даёт 0 различий.
