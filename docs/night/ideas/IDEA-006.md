# IDEA-006: Обещание не опережает свою проверку
- Критерий ТЗ: кр.1
- Цитата ТЗ: «Обещания соответствуют продукту.»
- Новизна: ни у кого из найденных в [COMPETITORS.md](../../COMPETITORS.md) и прочитанных карточках не описана именно машинная проверка условной формулировки PRM, подтверждение которого пока существует только как незавершённый EXP. Общие проверки обещаний есть, например, у [Chellenge](../research/cards/A-hfuvoo-art-chellenge.md); отсутствие этого частного механизма установлено только по описаниям, не по всему чужому коду.
- Что сделать: один локальный проверяющий инструмент `tools/promise_check.py <project> --json`: для каждого PRM пройти его `proof`; если там EXP без непустого `result`, потребовать в `PRM.message` явную пометку `после проверки EXP-NNN` для каждого такого EXP. Вывести PRM, EXP и `missing_condition`; отдельно показать отсутствующие или отозванные основания. Инструмент исполняет уже существующее правило `skills/strategy`, не придумывает обещаний и ничего не исправляет. Непустой результат эксперимента отмечается только как `result_recorded`, а не как успешная проверка; всегда `semantic_support: not_checked`.
- Польза, которую можно измерить: до — существующий validate проверяет наличие функции и связи с DEC, а условие незавершённого эксперимента остаётся текстовым правилом; после — на 3 контрольных PRM ровно 1 безусловное обещание при пустом EXP.result получает `missing_condition`, условное и обещание с фактическим основанием эту ошибку не получают. Проверяем число обнаруженных нарушений правила, без обещания доказать истинность сообщения.
- ИИ-время: ~40 мин
- Риск: поиск буквальной пометки не распознает все корректные перефразировки и не проверит соответствие функции смыслу обещания; формат пометки уже задан навыком, ограничение видно в JSON. Непустой `result` может описывать провал: инструмент не присваивает статусы `ready` или `confirmed` и не разрешает публикацию.
- Зона правок: `tools/promise_check.py`, `tests/test_promise_check.py`, новые `tests/fixtures/promise_check/**`.
- Черновик приёмки:
  1. `.venv/bin/python tools/promise_check.py tests/fixtures/promise_check/mixed --json` → код 1; среди 3 PRM ровно один `missing_condition`, перечислены правильные PRM-ID и EXP-ID; у всех результатов `semantic_support: not_checked`.
  2. `.venv/bin/python -m pytest -q tests/test_promise_check.py -k conditions_and_multiple_experiments` → код 0; условное сообщение проходит, два незавершённых EXP требуют обе пометки, пустая строка и отсутствие `result` равнозначны.
  3. `.venv/bin/python -m pytest -q tests/test_promise_check.py -k failed_result_missing_and_retracted` → код 0; непустой отрицательный результат получает только `result_recorded`, потерянная ссылка и отозванный EXP показаны ошибками, статусов `ready` и `confirmed` нет.
  4. `.venv/bin/python -m pytest -q tests/test_promise_check.py -k read_only_offline` → код 0; хэши проекта не изменились, вызовов сети и LLM 0, отсутствующий проект даёт код 2.
- Почему не дубль: T02 отображает обещания и ссылки, T04 проверяет исходную таблицу, T05 проходит демонстрационный сценарий; здесь автоматизируется конкретное правило условного обещания из навыка strategy. IDEA-001 считает разные файлы, 002 проверяет веса, 003 и I-01 собирают очередь, 004 сравнивает версии, 005 проверяет перенос. SYNTHESIS предлагает контракт сбора и отрицательные ответы без чисел, а не PRM → незавершённый EXP. IDEA-007 фиксирует условия эксперимента, но не формулировку сообщения.
- Тест МегаФона: 1 стратегия → коммуникации: руководитель видит, какое обещание пока условно · 2 сохраняются PRM/EXP-ID и непроверенный смысл, нет автоматического подтверждения продукта · 3 скрипт внутри существующей папки, без сервиса и новой зависимости · 4 на 3 PRM обнаруживается ровно 1 пропущенное условие, записей и платных вызовов 0.
