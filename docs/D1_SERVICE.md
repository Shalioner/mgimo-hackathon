# Рабочий локальный сервис D1

Среда: Codex внутри Orca, macOS, Apple Silicon. Сервис обслуживает локальную
`LiquidAI/d1-2B-MLX-8bit` через её штатный `model.system_one`. Весов, калибровки
и версии MLX-VLM не меняли. Лабораторный CLI сохранён отдельно.

## Запуск и управление

Из корня проекта:

```sh
.venv/bin/python tools/d1_control.py start
.venv/bin/python tools/d1_control.py status
.venv/bin/python tools/d1_control.py stop
```

`start` устанавливает только собственный LaunchAgent `local.strategist.d1`, запускает
его и ждёт доступности сокета. Повторный start не убивает работающую модель. `stop`
проверяет принадлежность job, останавливает сервис и подтверждает исчезновение endpoint.
Timeout/ошибка доступа означают unknown, а не stopped. Установленный LaunchAgent
стартует при следующем входе пользователя; остановка текущего экземпляра не удаляет plist.
Посторонние LaunchAgents и приложения не меняются.

Пути:

- `~/Library/LaunchAgents/local.strategist.d1.plist` — автозапуск;
- `~/.cache/strategist/d1-service/service.sock` — приватный UNIX socket;
- `~/.cache/strategist/d1-service/` — каталог 0700, socket 0600;
- существующий `~/.cache/strategist/d1-2b-lab/mlx-venv/` — закреплённые зависимости;
- существующие закреплённые MLX8 веса — без новой загрузки из сети.

LaunchAgent использует абсолютный путь к `tools/d1_service.py` в этом checkout.
Перемещение/удаление checkout требует обновления установленного job; installer
не перезаписывает отличающийся plist автоматически.

## Включение в Стратеге

Локальная конфигурация:

```yaml
automatic_routing:
  classifier: local-d1
  local_d1:
    mode: service
    socket: /Users/shalioner/.cache/strategist/d1-service/service.sock
```

Service — режим по умолчанию для local-d1. `mode: lab` явно выбирает прежний one-shot
CLI; при недоступности сервиса автоматического переключения на lab/cloud/API нет.

```sh
.venv/bin/python tools/route_request.py --prompt-file request.md --host codex --classify-only --execute
```

Этот вызов обращается к сервису и возвращает вероятности, принятые labels и рекомендации
модели/effort. Неуверенный ответ остаётся needs_review. Для автоматического исполнения
выбранной Luna/Terra/Sol/Astra по-прежнему нужен разрешённый профиль соответствующего host.
Сервис D1 не подменяет GUI integration и не выдаёт себе разрешений запуска облачных моделей.

## Жизненный цикл

Supervisor лёгкий и постоянно доступен. Первый infer загружает один изолированный worker;
следующие запросы используют тот же процесс и загруженную модель. Четыре запроса могут
ожидать в очереди, inference последовательный. Deadline включает очередь и загрузку;
просроченная задача не исполняется позднее. Повтор ID не запускает inference заново.
Status и stop доступны во время загрузки/вычисления.

После 300 секунд без вычисления модель выгружается. Supervisor остаётся; следующий запрос
без пригодного кэшированного результата снова загружает модель. `model_state=idle` означает доступный сервис без загруженной модели,
`loading` — загрузку, `ready` — модель загружена, `unloading` — реальное завершение worker,
`blocked` — отказ с причиной. `active_id` и `queue_depth` показывают текущую работу.
`worker_pid`, `generation`, `completed` позволяют отличить переиспользование от перезапуска.

При смерти supervisor worker отслеживает родителя и завершается. Общий inference.lock
исключает одновременную загрузку модели лабораторным CLI. Только worker имеет MLX runtime;
он запущен под macOS sandbox с запретом сети и минимальным env без API-ключей.
Путь к весам и lock передаются явно, а не вычисляются от изолированного HOME.

## Точный кэш и повторные задачи (2026-11-16)

По умолчанию сервис повторно использует успешный, прошедший проверку ответ для
точно одинаковых state и questions. Порядок вопросов и вариантов сохраняется.
Ключ включает repo/revision, SHA256 manifest (в том числе калибровку), версию
MLX-VLM и режим чтения вероятностей. Нет смыслового поиска похожих задач.

В RAM хранится до 128 результатов размером до 128 KiB каждый; срок пригодности
300 секунд от вычисления, попадание его не продлевает. Просроченные записи
удаляются при следующем обращении к кэшу, все записи — при завершении процесса.
Это не обещание стирания ровно через 300 секунд. Исходные запросы в кэш не
записываются, но ответы могут содержать извлечённые данные. На диск кэш не пишется.
Сервис приватен для одного пользователя ОС, не является многопользовательским
корпоративным API с разделением арендаторов.

Готовый результат возвращается без ожидания очереди. У уже стоящих в очереди
одинаковых задач кэш проверяется повторно при dequeue: после первого успешного
вычисления остальные могут не вычисляться. Это не немедленная рассылка всем
ожидающим: чужая задача перед дубликатом по-прежнему может его задержать.
Очередь остаётся ограниченной; каждый клиент имеет собственные ID/deadline/cancel.
Отмена первого вычисления не отменяет остальные задачи, которые при необходимости
вычислят ответ сами. Ошибки и отказы в кэш не попадают.

`runtime.reuse`: `miss`, `cache`, `queued`, `bypass`; `inference_calls`: 1 или 0.
У повторного ответа `usage` содержит ноль новых токенов, исходное значение
сохранено в `runtime.source_usage`. `worker_pid/generation` такого ответа —
происхождение результата, а не свидетельство работающего сейчас процесса.
Текущая живость — через status. `completed` считает реальные успешные вычисления,
`reuse.hits` — повторно использованные ответы. Очередь/загрузка/вычисление/возврат
по-прежнему разделены в timing. Кэш хранит ответ классификатора, не разрешение:
выбор исполнителя и актуальные разрешения проверяются роутером заново.

Для независимых измерений в `automatic_routing.local_d1` задайте `reuse: false`.
Это обходит чтение и запись кэша; при прямом UNIX-протоколе используется поле
`reuse: false`. Тесты качества и сравнения режимов отключают reuse явно.
Скрипт `evals/routing/d1_reuse_benchmark.py` сравнивает оба варианта на одном сервисе.
Разные новые запросы вычисляются как раньше; ускорение нельзя переносить на них
с нагрузки, состоящей из одинаковых запросов.

## Накладные расходы и native-вопросы (2026-11-16)

Worker возвращает `runtime.engine_timing`: подготовка входа в нашей обвязке,
вызов `system_one` с synchronize, проверка результата/очистка MLX cache.
`model_seconds` включает внутренние операции SDK, это не измерение чистого GPU.
На cache hit поля новых engine timings пустые, исходные — `source_engine_timing`.

Native host сохраняет собственные инструменты и не использовал ответ capability
как gate. Теперь `host_routing.compact_questions: true` (по умолчанию) спрашивает
только tier и effort. `false` возвращает прежние три вопроса. Остальной
`route_request` и отдельный delegate по умолчанию сохраняют capability.
Порог .75, разрешения, allowlist и T4 quota не меняются. Входной текст не обрезается.
Парный локальный тест: 20 разных кейсов, cache off, совпали все tier/effort choices
и восемь принятых маршрутов; median inference 2.148 → 1.760 с. Это малый
исследовательский тест, не доказательство качества на всех корпоративных задачах.
Исторические evals явно фиксируют три вопроса; новый протокол выделен отдельно.

На клиентской ошибке соединения/таймауте и KeyboardInterrupt адаптер делает
best-effort cancel только собственного UUID (до 2 секунд). Проверяет ID и статус
ответа отмены; неподтверждённая отмена явно `unconfirmed`. Inference автоматически
не повторяется. `cancelling` не равно уже завершённой отмене. SIGKILL/неперехваченный
SIGTERM и замена пользовательского запроса в host пока не дают такого обещания;
остаётся серверный deadline. Отменять по тексту или общему кэш-ключу нельзя.

## Ограничения и восстановление

Принимается текстовый state до 32768 bytes; до восьми типизированных вопросов по прежней
схеме; полный пакет до 65536 bytes. После tokenizer проверяется 4096 текстовых токенов,
перед forward — 8192 позиций подготовленного входа. Усечения нет. Это эксплуатационные
границы данного сервиса на 8 GiB Mac, не заявленный полный контекст модели. Media пока
остаётся в лабораторном интерфейсе; сервис предназначен для текстовой маршрутизации.

Повышенное давление памяти (pressure=2) не запрещает запуск само по себе. Supervisor
останавливает только свой worker при critical pressure>=4, RSS>6 GiB, общем swap>8 GiB
или росте swap>3 GiB за жизнь worker. Лимиты MLX/MPS и системные настройки не меняются.
После аварии — 30 секунд cooldown; новая попытка возможна по следующему запросу,
автоматического бесконечного перезапуска модели нет. Недостаток памяти не маскируется
переключением на более дешёвые веса или внешнего провайдера.

В журналах сервиса нет текстов источников и запросов. Caller получает ответ, вероятности,
usage и диагностический статус. Ошибки загрузки возвращаются по протоколу с фазой startup.

## Проверка

Offline регрессии проверяют настоящий IPC/subprocess lifecycle с fake engine: один PID
для повторных запросов, очередь и deadlines, восстановление, single-instance lock,
private permissions, корректную остановку, явные пути при изолированном HOME и диагностику.
Результаты живой приёмки сохранены в `docs/research/d1-service-2026-11-15/`.

возвращает отказ, а не скрытый переход на другие веса/внешнюю модель.

## Пять клиентов и измерение задержек (15.11.2026)

Admission теперь ограничивает суммарно5 запросов (один выполняется, четыре ждут),
включая одновременное поступление до первого dequeue. Шестой получает busy.
`runtime.timing` содержит queue_wait_seconds, worker_setup_seconds,
worker_roundtrip_seconds, worker_inference_seconds, server_total_seconds,
client_roundtrip_seconds, cold_start и completed. Неизмеренные стадии null;
completed означает завершение обработки запроса сервером, не успешный inference.

Живой [pilot пяти агентов](research/five-agent-d1-2026-11-15/README.md): первый
холодный старт заблокирован critical memory; во втором раунде10 ответов одним
worker, максимум client roundtrip39.54с при экспериментальном deadline120с.
По этому измерению default host deadline увеличен до120с: он включает очередь
и загрузку. Disconnect сам по себе не отменяет запрос; действует deadline. Нельзя обещать
устойчивую пятиагентную работу при любой фоновой нагрузке на8ГБ.

## Отмена по ID

В приватный socket отправляется `{"op":"cancel","id":"<ID своего запроса>"}`
через `d1_service.request`. Для queued возвращается cancelled, для active —
cancelling: окончательный infer receipt подтверждает отмену после завершения
собственного worker. Поздняя отмена возвращает already_finished, чужой/неизвестный
ID — not_found. Отмена active потребует загрузить worker на следующем запросе.
Отмена queued не выгружает worker; слот физически освобождается при dequeue.
Опубликованный результат отмены неизменен при последующем cooldown/shutdown.

Ошибки содержат runtime.phase и снимок pressure/swap/RSS. Лимиты памяти не снижены.
Offline регрессии включают отмену в очереди, активную отмену, гонки публикации
результата и восстановление. Live свидетельства обновляются отдельно.
