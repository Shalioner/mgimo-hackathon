# Pilot: пять агентов, один D1

Предрегистрация 2026-11-15, до inference. Разрешение — текущий запрос пользователя
на живые тесты пяти агентов, разных кейсов/моделей/effort и сравнение без D1.
Среда codex; текущая native подписка, локальный MLX D1; новых API/ключей нет.

## Дизайн

Пять независимых процессов-агентов, каждому два последовательных задания своего
синтетического кейса. Это ограниченные текстовые workflow через настоящий Codex
app-server, не пять субагентов в UI Orca и не полный продуктовый E2E C1–C3.
На каждом из двух шагов barrier одновременно выпускает пять процессов. Второй
шаг ждёт завершения всех первых: это намеренный тест burst-нагрузки, не свободный
поток пользовательских сообщений. Между шагами модель может меняться.

Два повторения, порядок: routed → manual → manual → routed. Всего по20 задач
на ветку, одни и те же10 уникальных заданий. Повторы не считаются новыми кейсами.
В routed D1 классифицирует исходный запрос и данные, не ответы/эталоны.
В manual модели/effort заранее назначены по каждому шагу компетентным человеком
(здесь — зафиксированным до запуска проектом эксперимента). Это сильный контроль,
а не заведомо дорогая Sol для простых задач. Initial selection различается,
проверка качества и ограниченная эскалация одинаковы.

Пять кейсов: извлечение→план, несопоставимые периоды→расчёт, смешение сегментов→
стандартизация, варианты с экономикой→stop/go, обещания→коммуникация/проверки.
Каждый шаг получает одинаковый фиксированный вход в обеих ветках. Предыдущий
ответ не подставляется в следующий, чтобы не смешивать эффекты разных контекстов.
Эталоны и критерии сохраняются в manifest, но не передаются исполнителям.

Текущий сервис до первого routed-burst должен быть idle: измеряется один холодный
старт, следующие запросы — прогретый worker. Если он выгрузится, реальные cold_start,
PID и generation покажут это; результаты не переименовываются в warm.
Кэш облачной модели не очищается; cached input фиксируется, порядок частично
компенсируется обратным повторением. Небольшая выборка не даёт общего causal вывода.

## Ограничения и остановка

Постоянные конфигурации не меняются. Только in-memory экспериментальная политика:
D1 deadline120с, native deadline120с на вызов, quality max_attempts2 одинаково обеим
веткам. T4 запрещён native transport; max/ultra не применяются. Разрешены только
текущие approved Luna/Terra/Sol. Нет автоматического переключения аккаунтов/API.
Нет повторов транспортных ошибок. Неудача не заменяется новым удачным прогоном.
Максимум на задачу: два исполнения, две проверки и для routed один T1-review
неуверенного D1. Лимит batch20мин. Отказ ресурсов/таймаут фиксируется как отказ.

## Метрики

- D1: client roundtrip, queue wait, worker setup (включая load), worker roundtrip,
  engine inference, server total; null для неизмеренных стадий. Сеть/socket,
  сериализация и парсинг не выдаются за чистую задержку передачи.
- Worker PID/generation и ID каждого запроса; сопоставление пяти ответов кейсам.
- Полное время каждой задачи и batch, итоговые статусы, число manual/needs_review,
  число попыток, настоящий маршрут task model/effort и отдельно verifier/reviewer.
- Native input/cache/output/reasoning tokens всех вызовов; reasoning уже входит
  в output. Локальный D1 отдельно. Отсутствующий usage — неизвестен, не ноль.
- API-эквивалент по зафиксированным Standard short-context ценам, проверенным по
  https://developers.openai.com/api/docs/pricing (15.11.2026), через tools/cost.py.
  Это не фактическое списание подписки; электричество D1 не измеряется.
- Качество: независимая механическая сверка чисел/меток и слепой разбор смысла.
  Quality verifier внутри workflow не считается независимым судьёй benchmark.
  Ответы с корректными числами, но неподтверждённым выводом, не получают полный pass.

Изменения моделей считаются отдельно от effort на той же модели; переход к T1
проверяющему не называется понижением сложности основного задания. Если повышений
по quality не было — так и пишем, не подменяем результаты искусственными отказами.
Сравнение экономии допустимо только вместе с качеством и долей выполненных задач.
Все отказы, raw receipts, хэши входов/кода сохраняются. Выбор лучшего повтора запрещён.

## Проверки сервиса отдельно от экономики

Offline: active1+waiting4, шестой busy, сроки включают очередь, просроченный не
исполняется; malformed/duplicate IDs и границы памяти по прежним тестам.
Отдельного cancel-by-ID API нет: disconnect не означает немедленную отмену.
Эту возможность не объявляем готовой. У native executor SIGTERM останавливает
его app-server; это другой механизм и другой процесс.
