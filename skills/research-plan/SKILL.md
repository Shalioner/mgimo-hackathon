# План исследования

Результат — `outputs/02_research_plan.md`.

## Процедура
1. Для каждого варианта, который просматривается уже сейчас (включая «оставить как есть» и «закрыть»), спроси: **«Что должно быть правдой, чтобы этот вариант был лучшим?»** Каждое такое условие — кандидат в вопрос исследования.
2. Оставь вопросы, для которых разные ответы ведут к разным вариантам. Остальные перенеси в «Отброшенные» с причиной.
3. Отсортируй по **цене ошибки × неопределённости**. Наверху — то, в чём мы меньше всего уверены и что дороже всего угадать неверно.
4. Для каждого вопроса укажи:
   - тип данных: рынок/конкуренты (сайты), клиенты (отзывы, интервью, опросы), поведение (таблицы и метрики), экономика;
   - конкретные разрешённые источники (только открытые или материалы пользователя);
   - **критерий достаточности** («два независимых источника, сходящихся в оценке», «данные за ≥3 месяца»);
   - бюджет: ≤3 раунда поиска.
5. Если данных заведомо не будет (например, внутренняя экономика), сразу отметь это как будущий пробел и предложи, как его закрыть позже (эксперимент, запрос данных).

## Подсказки по типу вопроса
- «Почему падает X» → сначала проверить, правда ли падает (периоды, единицы, сегменты), затем разбить по сегментам, затем искать причины.
- «Кому продавать» → сегменты × задача × текущая альтернатива × готовность платить.
- «Что сказать аудитории» → барьер понимания или выбора, а не список функций.

## Разделение работы

Один интегратор отвечает за ledger и зависимости. Выделяй независимые пачки источников или вопросов только когда польза превышает затраты передачи и проверки; маленькую связанную задачу выполняй последовательно. Не дели общую DEC или её ранжирование между писателями.

Для каждой пачки задай владельца, baseline, входы с хэшами/локаторами, зависимости, критерий достаточности и наблюдаемую приёмку по [task/result-контракту](../../docs/AGENT_TASK_CONTRACT.md). Укажи общий бюджет поиска, источников и вызовов: лимиты проекта не умножаются на число исполнителей. Зависимое задание использует принятый результат, а не черновик соседнего агента.

Передавай узкий контекст: вопрос, подтверждённый бриф, нужные ID через brief/trace и разрешённые фрагменты источников. Запиши, когда расширять его (противоречие, отсутствующий знаменатель/период, зависимость вне пакета). Нельзя молча обрезать доказательства или ограничения ради лимита; запроси недостающий фрагмент либо раздели независимые входы с сохранением локаторов.

До автоматического вызова обязателен billing preflight из контракта; выбор модели по route сам по себе не разрешает расход. При manual продолжай последовательную работу в уже выбранной человеком среде и T0-проверки, без автоматического переключения провайдера.
