# План исследования

Результат — `outputs/02_research_plan.md`.

## Процедура
1. Для каждого варианта, который просматривается уже сейчас (включая «оставить как есть» и «закрыть»), спроси: **«Что должно быть правдой, чтобы этот вариант был лучшим?»** Каждое такое условие — кандидат в вопрос исследования. На сопоставимом горизонте зафиксируй условия смены лидера. Если есть числовой порог, укажи предпочтительные действия по обе стороны и при равенстве.
2. Оставь вопросы, для которых разные ответы ведут к разным вариантам. Остальные перенеси в «Отброшенные» с причиной. Если один вариант оптимален на всём допустимом диапазоне (устойчивый лидер, упущение = `0`) — **стоп**, дополнительные проверки не нужны.
3. Отсортируй по цене ошибки и неопределённости. Без заданных вероятностей **не имитируй EVSI**. Если варианты сравнимы по вкладу и принято правило `minimax regret`, оцени максимальный упущенный вклад до проверки и остаток после её возможных исходов. Улучшение при идеальной информации задаёт верхнюю границу пользы. Если сопоставимых оценок нет, покажи порядок вопросов и условия, от которых он зависит.
4. Для каждого вопроса укажи:
   - тип данных: рынок/конкуренты (сайты), клиенты (отзывы, интервью, опросы), поведение (таблицы и метрики), экономика;
   - конкретные разрешённые источники (только открытые или материалы пользователя);
   - **критерий достаточности и реально разрешаемые исходы** («два независимых источника, сходящихся в оценке», «данные за ≥3 месяца» или какие интервалы относительно порога решения источник реально разделяет и какая остаточная неопределённость остаётся);
   - **граница бюджета**: `≤3` раунда поиска, а при наличии лимитов — денежный предел, задержка (если задана) и число слотов/проверок.
5. Если данных заведомо не будет (например, внутренняя экономика), сразу отметь это как будущий пробел и предложи, как его закрыть позже (эксперимент, запрос данных). Если уже выполненная проверка после расхода слота дала нечёткий результат и оставила неопределённость на пороге смены решения, зафиксируй это как **нарушение ожидаемой разрешающей способности**, пересчитай остаточный `minimax regret` на новом интервале без повторной покупки сверх слота/бюджета и передай остаточный выбор человеку.

## Выбор следующей проверки или источника
При отборе платной или ограниченной по бюджету/слотам проверки:
1. Для каждого источника сравни **полный расход** с **границей бюджета** и числом доступных проверок. Покажи **реально разрешаемые исходы** относительно порога, их влияние на действие и **остаточную неопределённость**. Учитывай задержку, если она задана, и складывай её с ценой, только когда обе выражены в деньгах.
2. При бюджете на одну проверку предложи **строго одну покупку или явный стоп**. Если используешь `minimax regret`, сравни остаточную потерю плюс расход каждой выполнимой проверки с потерей без проверки. Покупка оправдана при строгом улучшении. Остановись при устойчивом лидере, исчерпании слотов или отсутствии полезной проверки в бюджете. Если разделение исходов неизвестно, вывод об окупаемости условен.
3. Зафиксируй **условные действия после проверки** (какой вариант выбирать в каждом разрешаемом исходе и при ничьей), **границу бюджета и остаток** и **причины отбрасывания каждого конкурента** (не меняет действие/допустимые варианты, превышает бюджет, превышает верхнюю границу пользы, доминирован по расходу при тех же исходах). Изменение справочной/нейтральной метрики без изменения экономики и допустимых действий выбор не меняет.

## Подсказки по типу вопроса
- «Почему падает X» → сначала проверить, правда ли падает (периоды, единицы, сегменты), затем разбить по сегментам, затем искать причины.
- «Кому продавать» → сегменты × задача × текущая альтернатива × готовность платить.
- «Что сказать аудитории» → барьер понимания или выбора, а не список функций.

## Разделение работы

Один интегратор отвечает за ledger и зависимости. Выделяй независимые пачки источников или вопросов только когда польза превышает затраты передачи и проверки; маленькую связанную задачу выполняй последовательно. Не дели общую DEC или её ранжирование между писателями.

Для каждой пачки задай владельца, baseline, входы с хэшами/локаторами, зависимости, критерий достаточности и наблюдаемую приёмку по [task/result-контракту](../../docs/AGENT_TASK_CONTRACT.md). Укажи общий бюджет поиска, источников и вызовов: лимиты проекта не умножаются на число исполнителей. Зависимое задание использует принятый результат, а не черновик соседнего агента.

Передавай узкий контекст: вопрос, подтверждённый бриф, нужные ID через brief/trace и разрешённые фрагменты источников. Запиши, когда расширять его (противоречие, отсутствующий знаменатель/период, зависимость вне пакета). Нельзя молча обрезать доказательства или ограничения ради лимита; запроси недостающий фрагмент либо раздели независимые входы с сохранением локаторов.

До автоматического вызова обязателен billing preflight из контракта; выбор модели по route сам по себе не разрешает расход. При manual продолжай последовательную работу в уже выбранной человеком среде и T0-проверки, без автоматического переключения провайдера.
