# Анализ влияния новых сведений

Полный порядок действий — `workflows/update-decision.md`. Здесь главное.

1. Затронутое определяет **не модель, а граф**: `python tools/ledger.py impact projects/<case> CHG-NNN`. Не добавляй к списку объекты «на всякий случай» и не убирай из него — если не согласен, объясни почему в `run_log.md`.
2. Обновляй снизу вверх: CLM/HYP → ALT → DEC → PRM/EXP. Новую формулировку — новым объектом, старый — `ledger.py supersede`. Если объект попал в список, но по существу не меняется, добавь только `status_note` («проверено по CHG-NNN, без изменений») — так ты сэкономишь и токены, и внимание человека.
3. **Широкий список — не повод переписывать всё.** Если затронута большая часть реестра (обычно через «опорное» утверждение вроде «данных нет»), сначала пересмотри объекты глубины 1–2 из вывода impact, а более дальние только проверь по `status_note`.
4. Покажи человеку **diff решения**: для каждого затронутого объекта — было / стало / почему. Для демонстрации удобна цепочка:
   ```
   НОВЫЙ ИСТОЧНИК SRC-…
   ↓ CLM-… уверенность medium → low (противоречит CLM-…)
   ↓ HYP-… ослаблена
   ↓ ALT-… оценка «влияние» 4 → 2
   ↓ DEC-… требует пересмотра
   ```
5. Незатронутые артефакты не переписываются. В затронутых — **правка на месте**, а не только блок сверху: `tools/revise_lines.py projects/<case> --change CHG-NNN` правит необновлённые строки моделью T2 и перепроверяет; ты смотришь `git diff` и остаток (вручную — по списку `tools/verify.py projects/<case> --change CHG-NNN`). Документы целиком при пересмотре не перечитывай. Каждую перепиши («пересмотрено по CHG-NNN») или пометь «проверено по CHG-NNN». Пересмотр не закончен, пока список не пуст.
6. Новый выбор (если ранжирование изменилось) снова делает человек.
