# Верификатор утверждений

**Два прохода, чтобы не тратить сотни тысяч токенов.** Замер прогона 2: верификатор-модель, читавший весь пакет, съел около 412K токенов при ~70K на всю остальную работу.

## Проход 1 — код (T0, бесплатно)
```bash
python tools/verify.py projects/<case> --files 03 04 05 06 07 --sample 8
```
Код построчно проверяет `outputs/`:
- `unsupported` — число без ссылки на реестр;
- `wrong-ref` — ссылка на несуществующий объект (код выхода 1);
- `stale-ref` — ссылка на `retracted`/`superseded` (код выхода 1);
- `check` — чисел строки нет в объектах, на которые она ссылается;
- `sample` — N случайных строк «ok» для смысловой выборки.

`wrong-ref` и `stale-ref` исправь сразу сам: это механика.

## Проход 1.5 — модель решений (если настроена)
Строки `check` и `sample` можно сначала отдать классификатору: `python tools/decide.py --project projects/<case> --questions knowledge/decisions/source_supports.yaml --input <фрагмент источника> --items <строки как [{id, text}]> --step <N>`. Один вызов на пачку, ответ — шкала «противоречит … прямо поддерживает» и «преувеличено да/нет» с вероятностями. Уверенные ответы принимай, в проход 2 передавай только список «На проверку T1». Код 3 (провайдер не настроен) — сразу проход 2.

## Проход 2 — модель (T1), только по списку
Передай одним списком строки из прохода 1 и решающие основания, перечисленные ниже. Для каждого ID открой нужный фрагмент через `ledger.py trace projects/<case> <ID>`. Совпадающие фрагменты для одной проверки передай один раз. В Claude Code — субагент `claim-verifier` (haiku). В других средах — `tools/delegate.py --task verify-claims --input <вывод verify.py> --input <нужные фрагменты>`. Если выбрать модель нельзя, выполни эту сверку сам.

Для каждой строки вердикт:
- `ok` — подтверждено (число есть в источнике в другой записи, расчёт верен);
- `unsupported` — нет основания: добавить ссылку на CLM/HYP или пометить как допущение;
- `overstated` — формулировка сильнее источника (интерпретация как факт, «главная причина» при low, смена единиц или периода);
- `wrong-ref` — ссылка не на то.

Строки `sample` проверяются только на `overstated`.

### Смысл основания и обещаний

Совпадение цитаты, числа или ID не доказывает вывод. Для проверяемой строки сверяй
сегмент, период, единицу, отрицания и силу формулировки. Нельзя переносить результат
прошлого периода на текущий или превращать гипотезу в установленный факт.

Перед C3 включи в список все основания, которые могут изменить выбор, порог или
обещание. Найди их по действующему DEC, сравнению выбранного варианта с ближайшей
альтернативой, EXP и PRM. Для каждого сверь утверждение с цитатой или локатором,
включая числитель и знаменатель. Запиши вердикты по ID в `state/verification.md`.
Результат числовой проверки `numbers_matched` означает совпадение чисел.

Перед C3 отдельно просмотри **все активные PRM** и только их `proof` через `trace`:
измеряет ли основание именно обещанное свойство? Конверсия не доказывает цену,
скорость покупки или автоактивацию. План EXP без результатов — будущая проверка,
не подтверждение готового продукта. Нет прямого основания — `unsupported`; ссылка
на проверку другого свойства — `wrong-ref`. Сними сообщение с использования до
проверки; ошибочную запись сохраняй с lifecycle-меткой, не выдумывай доказательство.
Новые сообщения и существенные изменения принятого пакета требуют C3.

Контрольные негативные и корректные примеры: `evals/semantic/cases.json`.
Офлайн-проверка корпуса и оценка вердиктов не являются замером точности модели.
