# План проверки

Результат — EXP в реестре и `outputs/07_validation_plan.md`, checkpoint **C3**.

## Процедура
1. Возьми все HYP с `would_change_decision: true` и все допущения, на которых держится выбранный вариант (`ledger.py trace DEC-…`).
2. Для каждой — эксперимент EXP с явным типом **`discovery`** или **`causal`**:
   - для **`discovery`** допустима малая выборка (например, `n = 6` интервью/наблюдений) с явной пометкой **«не основание для масштабирования»**;
   - для **`causal`** (A/B, оценка причинного эффекта) обязательны:
     - **метрика** строго как `числитель / знаменатель`;
     - **с чем сравниваем** — контрольная группа, предыдущий период, другой сегмент;
     - **база** (исходная доля/уровень) и **MDE** (минимально обнаружимый эффект);
     - **n на группу** по расчёту через `python tools/power.py n --p … --mde …` (и `mde` / `wilson` при оценке);
     - **окно наблюдения** (`duration`) не короче **цикла поведения** и когда смотреть промежуточные данные;
     - **нежелательные последствия** — что может ухудшиться (каннибализация, нагрузка, жалобы);
     - **stop/go** — числовой порог stop, явно выведенный из **точки безубыточности M08**;
     - ответственный (роль).
3. Приоритет: сначала дешёвые проверки (фейковая дверь, опрос, прототип), потом дорогие.
4. Проверь честность: если гипотезу невозможно опровергнуть выбранным экспериментом, переделай эксперимент.
   Сверь с EXP и DEC окно наблюдения и логические связки условий (`и` / `или`). Порядок перечисления метрик не влияет на вывод. Проверь положительный, отрицательный, пограничный результат (сохраняй точный знак `<` против `≤`, `>` против `≥`) и одновременное срабатывание `stop` и `go`:
   - **конфликт `stop` и `go`:** примени согласованный приоритет. Если его нет, вынеси на **C3** предложение сначала применять ограничения `stop`, затем проверять полноту данных и условия `go`;
   - **серая зона (неопределённость):** данных достаточно, но результат не удовлетворяет условиям ни `stop`, ни `go`. Укажи действие до следующего разбора и оставь масштабирование на паузе;
   - **неполные данные:** если наблюдений уже достаточно для выполнения `stop` с учётом всех связок, покажи этот исход сразу. Если ни один `stop` не подтверждён и для решения не хватает данных или окно ещё идёт, укажи **недостаток данных** и назови, что нужно собрать до `go`;
   - **ранние сигналы (тревога):** операционные сигналы без утверждённого порога **не подменяют** согласованные `stop/go` (отдельно от решения по пилоту) — назначь измеримую диагностику и при необходимости вынеси числовой порог на **C3**;
   - **удержание и оформление:** не приравнивай «не ухудшилось» (например, равный отток) к доказанному улучшению — для него нужны определение метрики, окно наблюдения и заранее согласованный полезный эффект. Для каждого сценария укажи **измеримый следующий шаг** и **место согласования (C3)**; не заменяй утверждённые условия своими порогами.
5. **Перед C3:** `ledger.py validate` = 0 ошибок, `python tools/strategy_checks/validation.py projects/<case>` = 0 ошибок, `python tools/verify.py projects/<case> --files 07 --strict`, `python tools/consistency.py projects/<case>` и верификатор (`skills/claim-verifier`) по всем `outputs/`.
   В «Главном» укажи ближайшую проверку, срок, действующие условия остановки и продолжения и отдельно обозначь предложения к C3.
   Учитывай ограничения кодовых ворот: `validation.py` на legacy-таблице выдаёт `warn` с кодом `0` и не сверяет логику составных `stop_go` (связки, знаки, приоритеты), а `verify.py` в `07` не проверяет логику табличных строк `EXP-`. Кодовые проверки **не утверждают C3 автоматически** — приоритет при конфликте и уточнения условий утверждает только человек на **C3** (`tools/c3_approval.py`).
